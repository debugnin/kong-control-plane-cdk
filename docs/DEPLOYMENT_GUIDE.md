# Deployment Guide

## 1. Prerequisites

- Node.js 20+, npm, AWS CLI v2, `openssl`, `jq`
- AWS credentials for the target account and region (`aws sts get-caller-identity`)
- CDK bootstrap in that account/region:
  ```bash
  npx cdk bootstrap aws://<account-id>/<region>
  ```
- Kong Enterprise license file (`license.json`)
- Kong Gateway Enterprise image available to the VPC. Mirror it to ECR if the VPC has no route to Docker Hub (the NAT gateway provides egress by default, but private ECR is recommended for production)
- Either an ACM certificate ARN for the Manager/Admin API hostname, or a Route 53 hosted zone so CDK can request one

## 2. Create the supplied secrets

```bash
./scripts/create-cp-secrets.sh dev ./license.json ap-southeast-2
```

This creates `kong/cp/dev/license` and `kong/cp/dev/cluster-cert` and prints their ARNs. Existing secrets are left untouched. To use your own PKI for the cluster certificate, create the second secret yourself with keys `cluster_cert` and `cluster_cert_key` (PEM).

Aurora credentials, the Kong super-admin password and the Manager session secret are **generated by the stack** – nothing to create.

## 3. Fetch the RDS CA bundle

```bash
./scripts/fetch-rds-ca.sh ap-southeast-2
```

Kong verifies the Aurora certificate, so the regional RDS CA bundle must exist at `certs/rds-ca-{region}.pem` before synth (the stack fails with a clear message if it is missing). The file is public and is committed with the project.

## 4. Configure

```bash
cp config/dev.json.example config/dev.json
```

Edit at least: `kongImageUri`, `kongLicenseSecretArn`, `clusterCertSecretArn`, `albDomain` (or `albCertificateArn`), `albAllowedCidrs` and `dataPlaneCidrs`. `config/*.json` is git-ignored. Every key is listed in the [README](../README.md#configuration).

## 5. Review and deploy

```bash
export ENVIRONMENT=dev
npx cdk synth
npx cdk diff
npx cdk deploy --all
```

Deployment order is network → database → service. First deployment takes roughly 20–30 minutes, mostly Aurora. During service start the `kong-migrations` container bootstraps the schema and creates the super-admin; if it fails, the task stops and ECS retries – check the log group `/aws/ecs/kong-cp-logs-{env}`.

## 6. First login

```bash
aws secretsmanager get-secret-value --secret-id kong/cp/dev/admin \
    --query SecretString --output text | jq -r .password
```

Open the `KongManagerUrl` output (reachable only from `albAllowedCidrs`) and sign in as `kong_admin`. Change the password and create named RBAC admins; the generated secret is only used at bootstrap.

Admin API check (RBAC is enforced, so a token is required):

```bash
curl -s -H "Kong-Admin-Token: <password>" "$(aws cloudformation describe-stacks \
  --stack-name kong-cp-service-stack-dev \
  --query "Stacks[0].Outputs[?OutputKey=='KongAdminApiUrl'].OutputValue" --output text)/status"
```

## 7. Verify

- ECS service `kong-cp-ecsservice-{env}` shows the desired number of running tasks, and both ALB target groups are healthy
- NLB target groups for 8005 and 8006 are healthy
- Aurora cluster `kong-cp-db-{env}` is `available` with one writer and the configured readers
- AWS Backup → Backup plans → `kong-cp-backup-plan-{env}` exists. Trigger an on-demand backup of the cluster once and confirm it completes (see [BACKUP_AND_RECOVERY.md](BACKUP_AND_RECOVERY.md#verify-backups))
- Connect a test data plane using the [outputs](ARCHITECTURE.md#connecting-data-planes)

## Updating

| Change | How |
|---|---|
| Kong image tag, task size, replicas, log level | Edit config → `npx cdk deploy kong-cp-service-stack-{env}` (rolling, with circuit-breaker rollback) |
| Aurora capacity range, reader count, retention | Edit config → `npx cdk deploy kong-cp-database-stack-{env}` |
| Backup schedule/retention | Edit config → `npx cdk deploy kong-cp-database-stack-{env}` |
| Admin/CP access CIDRs | Edit `albAllowedCidrs` / `dataPlaneCidrs` → deploy service stack |
| **Switch the ALB between internal and internet-facing** (`albInternetFacing`) | **Requires recreating the service stack** - see below |
| Rotate cluster certificate | Update the secret, update all data planes, then force a new deployment: `aws ecs update-service --cluster kong-cp-ecscluster-{env} --service kong-cp-ecsservice-{env} --force-new-deployment` |

Changing `dbEngineVersion` triggers an Aurora engine upgrade; review `cdk diff` and test against a snapshot restore first.

## Switching the ALB between internal and internet-facing

An ALB's scheme cannot be changed in place, and an in-place update fails because the replacement ALB's listeners need target groups that the old ALB still holds (a target group can belong to only one load balancer). Recreate the service stack instead; the database stack, backups and secrets are not affected:

1. Set `albInternetFacing` and `albAllowedCidrs` (for example your public IP as a `/32`) in `config/{env}.json`. An internet-facing ALB with the default VPC CIDR is public but unreachable.
2. `npx cdk destroy kong-cp-service-stack-{env}`
3. `npx cdk deploy --all` - always `--all` (never `--exclusively`): the network stack must publish the public subnet exports first.
4. Delete the retained WAF log and ALB access-log buckets from the old stack.

Expect 15-20 minutes without Manager or the Admin API, a new NLB hostname (update any data planes that use the old one), and a new ACM certificate. Keep the ALB internal for anything beyond development and reach it over a VPN or Transit Gateway.

## Upgrading Kong

Only `kong migrations bootstrap` runs automatically. For a version upgrade that includes schema changes:

1. Take an on-demand AWS Backup of the cluster.
2. Run the up-migrations from a one-off task using the **new** image, with the same environment and secrets as the `kong-migrations` container:
   `kong migrations up`
3. Roll the service to the new image (`cdk deploy` with the new `kongImageUri`).
4. When all tasks (and data planes) are on the new version, run `kong migrations finish` the same way.

Follow Kong's upgrade guide for the specific version path; never run `finish` while old-version nodes are still serving.

## Teardown

Dev only. With deletion protection on, the database stack cannot be deleted:

1. Set `"dbDeletionProtection": "false"` and redeploy the database stack (this also lifts termination protection).
2. `npx cdk destroy --all`

Retained after destroy (by design): the AWS Backup vault and its recovery points, KMS keys, generated secrets, the final Aurora snapshot, the ALB access log bucket and the WAF log bucket. Delete them manually when no longer needed (recovery points must be deleted before the vault).
